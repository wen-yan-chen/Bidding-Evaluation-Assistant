# 开发说明

> 面向改代码的人：目录结构、处理链路、模块职责、改规则/改判据的标准动作、测试与 CI。
> 使用页面做评审的人看 `使用说明.md`；样本与数据看 `数据说明.md`；评测结论看 `评审说明.md`。

## 一、目录结构

```text
api/                     后端（FastAPI）
  main.py                应用入口、静态资源挂载
  config.py              路径与配置（DATA_DIR、上传上限、管理员账号）
  parsers/               docx / pdf / txt 解析、OCR、条款切分
  extract/fields.py      字段抽取（8 个字段：项目名称、编号、采购人、投标人、报价、工期、资质清单、业绩清单）
  review/qualification.py 资格性三态核验（R01–R10）
  review/service.py      一次评审的总编排（资格性 + 评分 + 风险）
  scoring.py             评分引擎（price_ratio / duration / presence）
  rules.py               40 条规则库加载、指纹、风险扫描
  report/                报告构建与 docx/pdf 导出
  routes/                HTTP 路由（review / docs / report / rules / health / admin / meta）
  store.py               解析结果、评审、报告的落盘
  docmodel.py            文档模型（full_text、页码映射、slice_text、page_of）
web/                     前端（原生 JS，无构建步骤）
data/                    规则库、评分细则、样本、解析/评审/报告产物
knowledge/               规则库导出的知识库（rules-full.md + 单条 md + manifest）
tools/                   校验、评测、样本生成、知识库导出
tests/                   pytest（API、解析、评分、规则、报告、风险）
docs/                    文档（本文件、数据说明、评审说明、使用说明、截图、样例报告）
```

### 2.2 模块职责

| 模块 | 职责 | 关键文件 |
| --- | --- | --- |
| `api/main.py` | FastAPI 应用、静态资源、路由挂载 | `api/main.py` |
| `api/config.py` | 路径、上传上限、管理员、版本 | `api/config.py` |
| `api/parsers/` | docx/pdf/txt/md 解析、OCR、页映射、条款切分 | `parsers/*` |
| `api/extract/` | 8 字段抽取（含资质/业绩清单条目） | `extract/fields.py` |
| `api/review/` | 资格性三态、评分、风险、报告编排 | `review/qualification.py`、`review/service.py` |
| `api/scoring.py` | 价格/工期/presence 评分；默认 calibrated | `scoring.py`、`data/scoring/*.yaml` |
| `api/rules.py`、`api/checks.py` | 40 条规则加载、门控、扫描、计算型规则 | `rules.yaml`、`checks.py` |
| `api/report/` | 九章报告、docx/pdf、数值复算 | `report/builder.py`、`*_export.py` |
| `api/store.py` | 解析/评审/报告落盘与索引 | `store.py` |
| `web/` | 原生 HTML/CSS/JS，无构建步骤 | `web/index.html`、`app.js` |
| `mcps/` | MCP 入口，依赖 `api/`，不是独立服务 | `bid_review_mcp.py` |
| `knowledge/` | 规则库导出的知识库与指纹 | `rules-full.md`、`manifest.json` |

### 2.3 请求链路

```text
POST /api/docs
  → 保存上传件 → parsers.parse → extract.extract_fields → store
POST /api/review
  → qualification.check（R01–R10，按 project_type 门控）
  → scoring.score_doc（默认 profile-a-calibrated）
  → rules.scan_doc（40 条，按 project_type 门控）
  → review 落盘
GET /api/report/{review_id}
  → report/builder → docx/pdf
```

关键原则：**算分/判定是确定性代码，模型不参与打分**；每个结果项都带 `page + quote`，
没有溯源的结果不进入报告。

### 2.4 部署拓扑

| 形态 | 组成 | 端口 |
| --- | --- | --- |
| Docker Compose | `app` + `mcp` 两个服务，共享 `./data` | app `18080`、mcp `8765` |
| 本地开发 | uvicorn 直接跑 `api.main:app`，MCP 可选 | app `18080` |
| AgentsHub | 只提交智能体包（`agent.json`、`skills/`、`mcps/`、`knowledge/`） | 平台托管 |

## 三、处理链路

```text
上传 → 解析（parsers）→ 字段抽取（extract）→ 评审（review/service）
                                              ├─ 资格性核验 qualification.check
                                              ├─ 评分 scoring.score_doc（按 profile_id）
                                              └─ 风险扫描 rules.scan_doc（按 project_type 门控）
                                          → 报告（report/builder → docx/pdf）
```

每个结果项都带 `page` + `quote`（溯源），没有溯源的不进报告。算分全部是确定性规则，不经过模型；
模型只负责把 `reason` 写成人话。

## 四、关键约定

1. **依据三态**：`verified` 带法规名称+条号；`pending` 运行期一律输出「未检索到权威依据」；`na` 输出「经验判据，无法条依据」。`pending/na` 不得填 `basis`（`validate_rules.py` 会报错）。
2. **指纹**：规则库、评分细则、知识库各有一份哈希；报告与页面都显示，用于回溯「这次用的是哪版口径」。
3. **不编造**：抽不到的字段返回空，不猜默认值；页码是估算就标「估算」。
4. **幂等**：同一 `doc_id + profile_id` 重复评审结果一致；报告重复导出返回同一文件。

## 五、改规则 / 改判据的标准动作

**加或改规则（`data/rules/rules.yaml`）**

```powershell
python tools\validate_rules.py      # 条数、id、依据三态、basis 格式
python tools\export_kb.py           # 重新导出 knowledge/
python tools\split_kb.py            # 重新拆分单条 md
python tools\validate_rules.py      # 再校验一次指纹一致
```

- `detect`：`pattern`（关键词/正则自动扫描）/ `manual`（人工核对）/ `price`（计算型，D6 实现）；
- `basis_status` 只能用 `verified / pending / na`；
- 政府采购体系的规则加 `project_types: ["货物", "服务"]`，工程专属加 `["工程"]`。

**改评分判据（`data/scoring/*.yaml`）**

- 三项类型：`price_ratio`（报价比值分档）、`duration`（工期对档）、`presence`（章节/承诺是否提供）；
- 校准版用 `content_patterns` 代替 `patterns`，并可配 `content_number_patterns`（该词必须与「数字+时间单位」同现）；
- **不要改历史 profile**：新增 `xxx-calibrated.yaml`，默认细则在 `api/routes/review.py` 与 `api/review/service.py` 里指定；
- 改完必须跑 `python tools\eval_calibrated.py --strict`，否则 CI 会红。

## 六、项目类型门控

- `/api/review` 接收 `project_type`：`engineering` / `goods_services` / `unknown`；
- `rules.rule_applies(rule, project_type)`：规则未配 `project_types` 或类型为 `unknown` 时一律适用；
- 已门控 13 条（清单见 `数据说明.md` 第十节），其余 27 条为通用规则；
- 资格性核验同样受门控约束，工程标不会拿政府采购 17 条去套。

## 九、常见问题的定位顺序

| 现象 | 先查 |
| --- | --- |
| 评分全是 0 / 细则缺失 | `python -c "import api.scoring as s; print([p.id for p in s.list_profiles()])"` |
| 依据全是「未检索到权威依据」 | 规则 `basis_status` 是否 pending；`knowledge/manifest.json` 指纹是否与 YAML 一致 |
| 知识库与规则库不一致 | `python tools/export_kb.py --check`（注意：它比对含生成时间的整篇，隔分钟会误报不一致，看指纹即可） |
| 报告数字与页面不一致 | `python tools/check_report.py` 复算 |
| 扫描件字段为空 | 是否走 OCR、页面是否模糊；看解析结果里的 `degraded` / `empty_pages` |
| 资格性项数变少 | 是否传了 `project_type`（工程标会过滤政府采购体系规则） |

阶段之间的关系：

- M0/M1 是数据入口，M2/M3 是判定核心，M4/M5 是输出，M6 是验收；

- M2 的 `project_types` 是 M3 门控和报告口径的来源；
- M5 的所有展示数据都从 API 读取，不在前端预填分数。
