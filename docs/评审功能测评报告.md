#### 4.2.2 关键问题：效力不足与缺失混淆（P1）

**（a）合规否定式被误判为“效力不足”。** 合成文本 `QA20261116-qual-neg-compliant.txt` 中：

```
营业执照：已提供
……
社会保险：已缴纳社会保险
我方近三年内无重大违法记录，亦无行贿犯罪记录。
中小企业声明函：已提供
联合体协议：本项目不接受联合体投标，无需提供联合体协议。
项目负责人：项目经理 1 名。
```

实际三态：R01–R05 已提供，**R06/R07/R08/R09/R10 全部“效力不足”**。其中 R06（社会保险）、R08（中小企业声明函）、R10（项目负责人）在文本里明确“已缴纳/已提供/项目经理 1 名”，本应是“已提供”；R07 的“无重大违法记录”本身是合规声明，也被判“效力不足”。

**（b）“无”是单字符，24 字窗口会跨行误伤。** 本地纯函数用例 `相邻行无字干扰` 中，R01、R06、R07、R08、R10 共 5 项“已提供”全部被翻成“效力不足”——只因为附近出现了“无重大违法记录”/“无需提供”。

**（c）“未提供”被归为“效力不足”而非“缺失”。** 文本 `未提供营业执照` 得到 R01=`insufficient`（计数 0/1/9），而按三态常规语义应为 `missing`；文本 `无需提供社会保险缴纳证明` 得到 R06=`insufficient`，也无法表达“不适用”。如果按代码注释“检出表述+否定信号=需核对”来解释，这仍会让评标人员在“缺失”和“效力不足”之间无法区分。

| 用例 | 期望（人工） | 实际 | 差异 |
| --- | --- | --- | --- |
| 合规否定式（完整材料） | R01–R08、R10 已提供；R09 不适用 | R06/R07/R08/R09/R10 效力不足 | 至少 4 项明确已提供被误判 |
| 相邻行“无”字干扰 | R01/R06/R07/R08/R10 已提供 | 5 项全部效力不足 | 5/5 误判 |
| 明说“未提供营业执照” | R01 缺失 | R01 效力不足 | 缺失↔效力不足混淆 |
| 明说“无需提供社保” | R06 缺失/不适用 | R06 效力不足 | 语义不可表达 |

证据：`edges-raw.json`（qualification 段）、`qual-semantics.json`、`26-qual-semantics.log`。

**影响：** 资格性表/报告会把“已提供”显示成“效力不足”，要求评标人核对并不存在的效力问题；反过来又把真正“未提供”的材料说成“效力不足”，弱化“缺失”的严重性。**建议**：否定词按短语/句界处理，排除“无重大违法记录、无行贿犯罪记录、无异议、无需提供…”等合规否定式；把“未提供/未附/无”归 missing，把“过期/失效/无效/不满足”归 insufficient；为三态补单元用例与 UI 图例。**不建议只改文案**。

> 注意：官方 25 份样本中 `insufficient` 实际为 **0/250**，第三态没有被真实样本覆盖；所以不能仅凭 bid-001 的 10/10 就宣称“资格性 100% 一致”。25 份样本也没有逐项人工真值，无法计算全量一致率。

- **证据：** 完整材料用例 R06/R07/R08/R09/R10 全为 insufficient；相邻行用例 R01/R06/R07/R08/R10 全为 insufficient；`qual-semantics.json`、`edges-raw.json`。
- **影响：** 资格性表/报告把“已提供”显示为“效力不足”，评标人会被引导去核对不存在的效力问题；在真实标书里“无重大违法记录/无行贿犯罪记录”很常见，误判面可能很大。
- **建议：** 否定词改为短语级（“未提供/未附/缺失/过期/失效/无效/不满足…”），排除“无重大违法记录、无行贿犯罪记录、无异议、无需提供…”等合规否定式；按句/条款边界取上下文，不要用单字“无”；补三态单元用例。**不改代码由被测方实施。**

#### P1-2 “未提供”被归为“效力不足”，缺失/效力不足混淆（阶段 1 已修复）

- **现象：** `未提供营业执照` → R01=insufficient（0 已提供/1 效力不足/9 缺失），而不是 missing；`无需提供社会保险缴纳证明` → R06=insufficient，无法表达“不适用”。
- **复现：** `qual_semantics.py` 的 `明说未提供_营业执照` / `edges-raw.json` 的 `QA20261116-qual-neg-missing.txt`。
- **证据：** 上述 JSON 的 states/counts；UI/报告状态标签“效力不足”。
- **影响：** 三态语义被反转：真正缺失被弱化为“效力不足”，而“效力不足”本应表示“材料存在但无效/过期”。资格性结论会被误读。
- **建议：** 明确规则映射：未提供/未附/无 → `missing`；过期/失效/无效/不满足 → `insufficient`；在 UI/报告加三态图例；对“无需提供”增加“不适用”说明（或单独第四态），不要塞进 insufficient。

### P2（中：功能/性能/一致性问题）

#### P2-1 报告封面未编号，正文从“二、”开始（阶段 1 已修复）

- **现象：** docx/pdf 章标题为“二、评审依据…”到“九、免责声明”，封面“招投标评审报告”没有“一、”；内容 9 个标记齐全，但编号只有 8 个。
- **复现：** 任意评审生成 docx/pdf，检查段落标题；`report-quote-page-check.json` 的 `chapter_markers` 9/9，但 `headings` 8/9。
- **影响：** 读者会以为缺第一章；验收“九章齐全”只能按内容算，不能按编号算。
- **建议：** 封面加“一、封面与文档信息”，或把封面明确为“封面（不编号）”并在目录/说明中写“正文八章”。

#### P2-2 同一规则重复命中（R35）（阶段 1 已修复）

- **现象：** `risk-015.docx` 第 1、2 页各出现“美元”，API 返回 2 条 R35，`risk_total=2`；`eval_risks` 按集合只算 1 条。
- **复现：** 上传 risk-015 → `POST /api/review`；对比 `risks.csv` 与 `03-eval_risks.txt`。
- **影响：** 风险数虚高；同一问题重复展示；评测与运行时口径不一致。
- **建议：** 按 `rule_id` 去重（保留第一条/最强证据），或在 UI 合并为“1 条风险，2 处证据”；报告风险数按去重后计。

#### P2-3 `/api/documents` 暴露非法 doc_id `eval`，详情 400（阶段 1 已修复：列表过滤）

- **现象：** 文档列表含 `doc_id=eval`、`file_name=bid-001.docx`、`has_raw=false`；`GET /api/doc/eval` 返回 **400 文档 ID 格式不合法**；在评审看板下拉选中后，页面提示 **“读取文档详情失败：文档 ID 格式不合法”**，评审按钮禁用、当前文档停留在“详情读取中”。管理员数据管理里点预览显示“只有解析结果，没有上传原件”（友好），但列表本身不应出现该 ID。
- **复现：** `GET /api/documents`；`GET /api/doc/eval`；在 `#review` 选择 `eval`（`ui_eval.py`）。
- **证据：** `ui-reports-raw.json` 的 `eval_api`、`eval_preview`；`ui-eval.json`；`00-environment` 之前的 46 文档基线含 `eval`。
- **影响：** 列表项不可用；用户看到“格式不合法”而不是“文档不存在”；历史测试产物污染数据管理。
- **建议：** `list_docs` 过滤 `valid_doc_id`；迁移/清理 `eval.json`；对非法 ID 统一 404 而不是 400（或从 UI 过滤）。

#### P2-4 `/api/documents` 默认 200 条，>200 文档时旧记录在 UI 不可见（阶段 1 已修复：UI 显式 limit=1000）

- **现象：** 峰值 213 份解析结果时 `/api/documents` 只返回 200；管理概览返回 205；报告中心用 `knownDocs` 判断可用性，超过 200 的旧文档会被当作“文档不存在”隐藏/无法查看原件。
- **复现：** 造 >200 文档；`GET /api/documents` 观察 count=200；`GET /api/admin/overview` 观察 docs=205；报告中心对比。
- **证据：** `cleanup.json` 的 before（214 文档）、`ui-reports-raw.json` 的 admin_data（205）；`ui-raw.json` 的 doc_options=200。
- **影响：** 长期运行后历史评审“消失”；用户可能以为数据丢失；报告中心“隐藏不可用记录”会把正常旧记录误判为不可用。
- **建议：** UI 显式传 `limit=1000` 或加分页/搜索；报告中心以文档详情/管理概览为准，不只依赖前 200 条列表。

#### P2-5 23/10/7 口径未在评审 JSON/页面完整展示

- **现象：** MCP `scan_risks` 有 `scanned_rules=23`、18/5、10 人工、7 未实现、`scan_notes`；`/api/review` 只返回 risks；页面只写“需人工核对/未实现规则不在命中范围”，不列 23/10/7；报告列了 10+7，但没写“23 条自动”。
- **证据：** `20-mcp-scan.txt`；`web/app.js` 风险说明段；报告 docx 第 6 章。
- **影响：** 验收要求“23/10/7 如实标注”只在 MCP/报告部分满足；页面用户无法判断本次扫了多少条、哪些没扫。
- **建议：** `/api/review` 增加 `scan` 元信息（23/18/5/10/7/notes），页面风险卡展示；报告补“23 条自动”计数。

#### P2-6 OCR 冷启动/热启动相对 D9 基线回归

- **现象：** 冷启动 p50 35.1 s（max 45.6 s；另一 cold smoke 52.5 s）；热启动 p50 18.8 s / p95 26.3 s；D9 记录 13–16 s。UI/文档仍写“单份约 13–16 秒”。
- **证据：** `perf-raw.json`、`cold-extra.json`、`06-smoke_test.txt`、`perf-run.log`。
- **影响：** 首次扫描件等待明显长于承诺；用户可能重复点击/以为卡死；虽未触发 180 s 超时，但体验与文档不一致。
- **建议：** app 启动时预热 OCR 或首份走后台任务；把文案改为“首次约 35–50 秒，之后约 19 秒”；监控 OCR 单页耗时。

#### P2-7 批量删除 162 文档耗时 182 s

- **现象：** 管理员 `batch-delete` 分 80/80/2 三批删除 162 份测试文档，总耗时 182 s（≈1.1 s/份）；每删一份文档会全量扫描评审目录找引用。
- **证据：** `23-cleanup.log`（162 targets / 182.1 s）。
- **影响：** 数据管理页大批量清理可能超过浏览器/网关超时；演示时“清理重复文档”可能长时间无响应。
- **建议：** 按 doc_id 建索引/一次扫描评审；异步任务 + 进度；限制单次批量大小。
